Sentinel — Architecture

Runtime policy enforcement for AI agents. Every proposed agent action is evaluated against policy before execution and receives ALLOW, REVIEW, or BLOCK. Sentinel never executes tools itself; it is a gate, not an agent. Self-hosted: run one isolated stack per environment. Items marked planned are agreed but not yet built.

1. Trust summary for operators & auditors

Isolation

Each deployment is a dedicated stack: own API, dashboard, Postgres, Redis — run one per environment or team. There is deliberately no tenant column anywhere in the schema — leakage across stacks is impossible by construction, not by careful WHERE clauses. Engineer depth: §3, §6.

Auditability

Every decision is hash-chained (prev_hash → hash, SHA-256 over canonical content). Retention purges write signed checkpoints bridging deleted ranges; checkpoint signatures (Ed25519, per-deployment offline key) let anyone verify origin without trusting the database. Weekly anchor copies sit in immutable R2 storage. Engineer depth: §7.

Data handling

Action arguments are stored redacted; third-party judgment models receive redacted payloads only. Signals (Falco) are evidence, never auto-decisions; alerts from non-Sentinel containers are dropped at ingestion. Human approvals are first-class and audited — REVIEW never auto-converts. Engineer depth: §4, §5.

7. Audit & anchoring

Hash chain

Each stored decision carries prev_hash (previous head, or 64 zeros at genesis) and hash = SHA-256 over canonical JSON of the decision content (excluding the hash fields themselves). GET /v1/audit/verify (admin) recomputes the chain and reports {ok, checked, unchained, bridged, firstBadId}. Approval updates preserve links; legacy pre-chain rows are tolerated as unchained only before the chain starts.

Signed checkpoints

Purge writes a checkpoint of the newest deleted row before the gap, so a retention range stays verifiable. With AUDIT_SIGNING_KEY set (base64 PKCS8 Ed25519, per deployment, offline), the checkpoint carries a signature over canonical {id, createdAt, headId, headHash, deletedCount}. The verify endpoint returns anchorPublicKey + per-checkpoint signatureValid, enabling fully offline third-party verification. Without a key, checkpoints stay unsigned and the hash chain still verifies (integrity without origin).

Dashboard badge

Overview shows an OK/BROKEN stamp fed by a same-origin proxy holding server-side admin credentials. A broken chain is a stop-everything event, not a warning to style away.

8. Retention — in-app purge + R2 R2 planned

DELETE /v1/decisions?before=&includeApprovals=&limit= (admin): approved/rejected rows are audit evidence and survive unless includeApprovals=true; orphaned actions and old signals go with the purge; every purged range leaves a signed bridge checkpoint (§7).

Off-box: nightly compressed pg_dump to R2 (dumps/, 7 daily + 4 weekly via lifecycle rules) plus weekly {checkpoints, anchorPublicKey} exports (anchors/). Restore drill = download → scratch restore → chain re-verify ok:true. R2 free tier (10 GB, 1M/10M ops, zero egress) covers this ~1000× over for a first deployment.
